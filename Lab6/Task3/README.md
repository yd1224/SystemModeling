# КП6 — завдання 3: управління запасами холодильників

Модель завдання 4 із КП5 реалізована через справжній `PetriSim` бібліотеки PetriObjModelPaint. Час вимірюється у **тижнях**.

## Запуск

Потрібна JDK 21 або новіша. У терміналі IntelliJ / PowerShell:

```powershell
cd C:\Users\demce\КПІ\SystemModeling\Lab6\Task3
.\run.ps1
.\run.ps1 -ModelArgs '--verify'
.\run.ps1 -ModelArgs @('1000', '42')
```

Перший запуск моделює 10 000 тижнів із seed 20261101. Тривалість спостереження в умові не задана, тому її обрано для експерименту. Остання команда задає іншу тривалість і seed.

У IntelliJ можна також запустити `task3.Main` або `task3.Verification`. Код Task3 має пакет `task3`, щоб не конфліктувати з `Main` і `Verification` завдання 2.

Використовуються наявні `../Task2/vendor` і `../Task2/lib`. Тримайте Task3 поруч із Task2: копіювати бібліотеку чи завантажувати її повторно не потрібно.

## Відповідність умові та діаграмі

Джерела: завдання 4 у наданому звіті `КП5_Демченко.docx` та файл `Завдання_4_єдина_мережа.drawio` від 24.10.2026.

- Початковий запас `H = 72`; відкладені замовлення `B = 0`; очікувані холодильники `O = 0`.
- Надходження покупців — експоненціальні інтервали із середнім 0,2 тижня. Один покупець потребує один холодильник.
- За наявності товару відбувається продаж. За відсутності — покупець іде з імовірністю 0,8 або очікує поставки з імовірністю 0,2.
- Плановий перегляд відбувається кожні 4 тижні. Замовлення формується, якщо `IP = H + O - B <= 18`.
- Допоміжна позиція `D = 72 - IP`. Інформаційна дуга від D до `StartOrder` має кратність 54, перевіряє `D >= 54` і не забирає маркери.
- Партія формується миттєвим циклом: по одному маркеру з D до O та Dispatch. Розмір партії дорівнює D на момент рішення. Після формування IP дорівнює 72.
- Доставка багатоканальна із затримкою 3 тижні. Усі одиниці однієї партії відправляються і прибувають в один модельний момент.
- Під час приймання кожна одиниця вилучається з O і додається до H. Покупці, які вже чекають, мають перевагу перед новими.

У XML діаграми дуга `A_e20` виходить із приймання відкладеного замовлення, але має лише координату кінця без `target`. У коді вона під'єднана до D відповідно до формули та тексту КП5: нове відкладене замовлення збільшує B і D на одиницю.

Легенда діаграми згадує службову позицію M, хоча сам вузол і його дуги у файлі відсутні. У коді M містить один контрольний маркер і забезпечує атомарність миттєвих операцій. Це потрібно, бо `PetriSim.input()` спочатку запускає дозволені переходи, а вихід їхніх маркерів виконує `output()`. Без M нижчий за пріоритетом перехід міг би побачити тимчасово вилучений ресурс раніше, ніж вищий перехід поверне вихідні маркери.

M утримується до завершення всього формування партії або всього рішення «піти/чекати». Звичайні миттєві операції забирають і повертають M. Пріоритети з діаграми збережено: приймання та виконання відкладених замовлень — 3; продаж, початок замовлення і додавання одиниці — 2; відсутність товару, ймовірнісний вибір, відмова від замовлення та закінчення формування — 1. Конфлікти однакового пріоритету, крім заданого вибору 0,8/0,2, розв'язує бібліотека. Операції одного часу не додають тривалості до статистики.

## Структура коду

- `src/task3/InventoryModel.java`: 17 позицій, 13 переходів, дуги, запуск через `PetriSim.input()` / `output()`, накопичення статистики та інваріанти.
- `src/task3/Main.java`: запуск експерименту та друк результатів.
- `src/task3/Verification.java`: контрольні приклади із заздалегідь відомими результатами.

Випадкові інтервали генеруються як `-0.2 * ln(1-U)`. Для надходжень та вибору «піти/чекати» використано окремі генератори з seed. Підклас PetriSim змінює лише випадковий вибір між двома альтернативами на відтворюваний; перевірку умов, пріоритети, входи, виходи та календар переходів виконує бібліотека. Обробники завершення переходів лише рахують покупців і одиниці товару та фіксують моменти втрачених продажів.

## Показники

Середній наявний запас:

`meanStock = sum(H_k * dt_k) / T`.

Середній час між продажами, що не здійснилися:

`meanLostInterval = (lastLost - firstLost) / (lostCount - 1)`.

Для другого показника потрібні щонайменше два втрачені продажі; інакше він виводиться як невизначений. Це середнє інтервалів між зафіксованими втратами, а не `T / lostCount`.

Події точно в момент T включаються. Статистика останнього інтервалу обрізається на T. Кожен запуск виконується на новому екземплярі моделі.

## Верифікація

У звичайному запуску після завершення всіх миттєвих операцій кожного модельного моменту перевіряються:

```text
D = 72 - (H + O - B)
customers = sold + lost + B
initialStock + receivedUnits = H + sold
O = Dispatch + buffer(Delivery) + Arrived
orderedUnits = receivedUnits + O
```

Також контролюються невід'ємність маркування, збереження M та відсутність одночасно додатних H і B. Перевірки виконуються після замикання миттєвих подій: під час їх виконання частина маркерів тимчасово перебуває в переходах.

Команда `--verify` додатково перевіряє:

| Приклад | Очікуваний результат |
|---|---|
| До першого покупця | H = 72, середній запас 72 |
| Один покупець щотижня, T = 10 | 10 продажів, H = 62, середній запас 67,5 |
| IP = 19 на перегляді | Замовлення відсутнє |
| IP = 18 перед 4-м тижнем | Замовлення ще відсутнє |
| IP = 18 на 4-му тижні | Замовлено 54, O = 54 |
| До 7-го тижня / точно на 7-му | Поставка ще не отримана / усі 54 отримані |
| Імовірність відходу 1 / 0 за H = 0 | Усі йдуть / усі чекають |
| Втрати в моменти 1, 2, 3 | Середній інтервал 1 тиждень |
| Поставка і новий покупець в один момент | Відкладений попит задовольняється, товар коректно обліковується |
| Багато звернень без запасу | Частка втрат близька до 0,8 |
| Спостереження до 1,5 тижня | Середній запас `(72*1 + 71*0.5)/1.5` |
| Однаковий seed у двох експериментах | Результати збігаються |

Фактичний результат перевірок — `PASS`; вивід збережено у `verification.txt`.

## Експеримент і висновки

Фактичний запуск із T = 10 000 тижнів і seed = 20261101 дав:

| Показник | Значення |
|---|---:|
| Покупців | 49 571 |
| Продажів | 45 321 |
| Втрачених продажів | 4 250 |
| Покупців, які чекають наприкінці | 0 |
| Кінцевий наявний запас | 34 |
| Очікуваних одиниць наприкінці | 0 |
| Замовлень постачальнику | 715 |
| Замовлено / отримано одиниць | 45 283 / 45 283 |
| Середній наявний запас | 28,837833 |
| Середній інтервал між втраченими продажами, тижнів | 2,348652 |

Контрольні баланси: `49571 = 45321 + 4250 + 0`; `72 + 45283 = 34 + 45321`.

Політика підтримує додатний середній запас, проте не усуває дефіцит: між перевірками та протягом доставки товар може закінчитися. У цьому експерименті втрачено близько 8,57% усіх звернень. Це не суперечить параметру 0,8: він стосується лише покупців, які звернулися за відсутності товару. Середній інтервал 2,348652 тижня характеризує проміжки між усіма послідовними втратами; самі втрати можуть групуватися у періоди дефіциту. Відкладені замовлення включено в потребу поповнення та задовольняються після поставки.

Контрольні приклади й інваріанти підтверджують реалізовану логіку. Наведені числові показники є результатом одного експерименту; для оцінювання статистичної похибки потрібні повторні запуски, які не входять до цього мінімального виконання завдання.
